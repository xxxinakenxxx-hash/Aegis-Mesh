## U-03 自動操作の許可モデル
**確定：採用**

操作を次の3区分で管理する。

| 区分 | 扱い |
|---|---|
| 事前許可済み | 許可範囲内で自動実行可 |
| 条件付き許可 | 定義済み条件を満たす場合のみ自動実行可 |
| 範囲外 / 禁止 | 停止し、人間判断へ戻す |

工程またはタスク単位で最低限、次を持つ。

```text
scope
allowed_actions
forbidden_actions
side_effect_policy
approval_required_if
```

人間の明示承認は、個別操作ごとではなく、工程開始時の許可範囲設定でも成立する。

許可範囲内では個別再承認を要求しない。

## U-04 Git操作の自動許可範囲
**確定：採用**

### 自動実行可
対象リポジトリ・対象branch・対象工程・変更範囲が明示されている場合に限る。

- status / diff / log 等の参照
- 作業branch作成
- 対象ファイルの作成・更新
- commit
- 通常push
- PR作成

### 条件付き自動
- merge
  - 対象工程で許可されている

  - BLOCKEDがない
  - 未解決事項が完了条件を妨げていない
  - 禁止事項に抵触していない

### 禁止
- force push
- 履歴改変
- repository削除
- branch削除
- 指定外repository変更
- 指定外branch変更
- 指定外ファイル変更

範囲外操作が必要になった場合は停止する。

## U-19 BLOCKED後の正式な遷移
**確定：採用**

BLOCKEDは、自動継続できない状態とする。

```text
BLOCKED
  ↓
人間判断
  ↓
再開 / 中止
```

自動Retry可能なものはBLOCKEDへ入る前に処理し、BLOCKED後にAIだけで勝手に再開しない。

## U-20 完了条件未達時の再検討フロー
**確定：採用**

完了条件未達を検知した場合、場当たり的な実装継続や試行回数の増加を防ぐため、いったんSTOPする。

```text
完了条件未達
  ↓
STOP
  ↓
AIが未達理由を分析・再検討
  ↓
プロンプト不備 / 指示不足 / 実装ミス / 環境要因 等に分類
  ↓
修正方針を定める
  ↓
再実行
```

人間判断へ戻すのは、仕様判断が必要、方針が一意に決まらない、許可範囲外の操作が必要、同一失敗を繰り返す、AI側で原因を特定できない場合とする。

Retryは、一時的なエラー等に対して同じ正しい処理を再試行する場合に限定する。設計・指示・実装方針が正しいか不明な状態で、実装を繰り返してはならない。

# 2. Phase 0で未確定の事項

## U-22 完了条件未達フローとRetryの関係
**未確定：要整理**

企画概要書の基本フローでは、完了条件未達後に自動Retryへ進める構造が残っている一方、U-20では「完了条件未達 → STOP → AIが原因分析・再検討 → 修正方針確定 → 再実行」としている。

確認すべき論点：
- 完了条件未達時は必ず一度STOPするか
- Retryは通信失敗・一時エラー等の技術的再試行だけに限定するか
- 完了条件未達とRetryを別系統として扱うか
- STOP後の原因分析・再検討を担当するAIは誰か
- 原因がプロンプト不備・指示不足の場合、誰が修正指示を作るか

現時点の推奨：
- 完了条件未達は必ず一度STOPして再検討する
- Retryは、一時的な失敗に対する同一処理の再試行に限定する
- 設計・指示・実装方針が正しいか不明な状態ではRetryしない
- 原因分析・再検討はChatGPT（設計・管理者AI）が主担当とし、Codex親は実行結果・失敗内容・証跡を返す
- 原因が実装手順やプロンプトにある場合は、ChatGPTが修正指示を再定義してから再実行する
