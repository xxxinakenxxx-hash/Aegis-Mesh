# 1. Aegis Meshとは何か

Aegis Meshは、複数のAIを安全に働かせるための管制システムである。

目的はAIを増やすことではない。人間、ChatGPT、Codex親、Subagents、Claude Code等が、同じ正本、同じ現在状態、同じ制約、同じ完了条件、同じ証跡を基準に仕事を進め、間違った前提が次工程へ伝播しないようにすることである。

Aegis Meshが防ぐ対象は次である。

- 正本を読まずに進む
- 未確定事項を推測で補う
- 指示不足やプロンプト不備を確認せず試行だけを増やす
- 誤った前提を別AIへ引き継ぐ
- 工程を飛ばす
- 許可範囲外へ作業を広げる
- 実装者の自己申告だけで完了扱いする
- テスト未実施や証跡不足を見逃す
- 同じ失敗を繰り返す
- 人間がAI間のコピペ係になる
- 人間とChatGPTが別の状態を見て判断する

# 2. 基本思想

## 2.1 AIを無条件に信用しない

Aegis Meshは、AIが必ず正しく理解する、必ず指示を守る、前回の文脈を必ず保持する、という前提で設計しない。

重要な制約はプロンプトの注意書きだけに依存させず、外部状態、契約、証跡、ゲート、許可範囲で確認できる構造にする。

## 2.2 人間は監視係ではない

人間は主に次を担当する。

- 目的・方針
- 重要仕様判断
- 許可範囲の設定
- AIだけでは決められない事項の判断
- 人間確認が必要な工程の確認
- BLOCKED後の再開または中止判断

人間にAI間のコピー&ペーストや、各AI画面の常時巡回を求めない。

## 2.3 ChatGPTは司令塔だが無制限なRootではない

ChatGPTは設計・管理者AIとして、何をするか、どの実行経路を使うか、結果をどう解釈するか、次に何をするかを決める。

Aegis MeshはChatGPTも統制対象とする。ChatGPTの判断であっても、正本、許可、証跡、状態遷移条件を飛ばして実行してよいわけではない。

## 2.4 プロンプト非依存

「必ず読め」「必ず記録しろ」「勝手に進むな」と書くだけでは統制としない。

重要なルールは可能な限りAegis Mesh側の状態、契約、ゲート、実行条件として実装する。

## 2.5 案件別コンテキスト分離

案件、工程、タスクごとに、参照正本、許可範囲、現在状態、証跡を分離する。別案件や別工程の情報を混在させない。

## 2.6 理解してから実行する

仕事を渡しただけで実装開始しない。実行前に、目的、対象、許可範囲、禁止事項、成果物、完了条件、参照正本、Context Versionが一致していることを確認する理解ゲートを持つ。

# 3. 全体構成

```text
人間
  ↕
ChatGPT
  設計・管理者AI / AI秘書
  ↕
Aegis Mesh
  管制層
  ↕                 ↕
Codex親            Claude Code
現場監督            別経路の実装実行系
  ↓
Subagents
調査 / 実装 / テスト / レビュー

Aegis Mesh
  ↕
GitHub
正本 / 状態 / 証跡 / 履歴

人間
  ↕
Vercel管制画面
```

役割は次のとおり。

| 主体 | 主な責務 |
|---|---|
| 人間 | 目的、方針、重要仕様、許可、人間判断 |
| ChatGPT | 要件整理、仕事定義、実行経路選択、結果解釈、再指示、工程判定 |
| Aegis Mesh | 状態、契約、制約、証跡、完了条件、Retry、BLOCKED、承認待ち、履歴整合を管制 |
| Codex親 | 作業分解、Subagent割当、並列実行、進捗統合、結果統合 |
| Subagents | Codex親配下で調査、実装、テスト、レビュー等を実行 |
| Claude Code | Codex親とは別経路で工程単位に選択される実装実行系 |
| GitHub | 正本、計画、TASK、状態管理の基盤、証跡、変更履歴 |
| Vercel管制画面 | 人間向けの専用管制画面 |

# 4. Work Contract

AI間で仕事を渡す際は、自然言語だけに依存せず、工程・タスクごとにWork Contractを持つ。

最低限の項目は次とする。

```text
project_id
task_id
process_id
context_version
objective
canonical_refs
scope
allowed_actions
forbidden_actions
side_effect_policy
approval_required_if
required_outputs
completion_condition
next_state
```

必要に応じて担当主体、repository、branch、対象path、環境、必要証跡、必要テスト、期限等を追加する。

Work Contractにない仕様を実装者AIが勝手に補完しない。

---

# 5. 正本とContext Version

各タスクは、どの正本のどの版を前提にしているかを特定できなければならない。

最低限、正本文書のpathとcommitまたはblob SHAを保持する。

タスク開始時に取得した正本と、実行または反映直前の正本が一致しない場合は自動継続しない。

Context Version不一致は停止条件とする。

---

# 6. 理解ゲート

実行者はWork Contractを受け取った直後に実装へ進まない。

次を確認する。

- 目的
- 変更対象
- 変更禁止対象
- 参照正本
- Context Version
- 必須成果物
- 必須テスト
- 完了条件
- 外部作用の許可範囲
- 次の状態

理解できない、矛盾する、複数解釈が成立する場合は実行しない。

---

# 7. Result Packet

実装者AIやCodex親は、「完了しました」だけで結果を返さない。

最低限、次を含むResult Packetを返す。

```text
project_id
task_id
process_id
context_version
actor
status
claims
changed_files
unchanged_scope
tests
test_results
evidence
diff_summary
side_effects
unresolved
blocked_reason
retry_count
result
next_recommendation
```

Result Packetの主張はEvidenceと照合できることを必須とする。

---

# 8. 状態管理

Aegis Meshでは、管制状態と実行主体状態を分ける。

管制状態：

```text
未着手
実行中
確認中
修正必要
BLOCKED
完了
中止
```

実行主体状態：

```text
待機
実行中
完了
失敗
```

`人間確認待ち` は追加フラグとする。

`人間判断` はBLOCKEDを解除するための判断工程として扱う。

状態遷移は、AIが文章で宣言しただけでは成立しない。必要な条件と証跡がそろった場合のみ成立する。

---

# 9. STOP / Retry / Replan / BLOCKED

## 9.1 完了条件未達

完了条件未達時は、試行だけを増やさず、いったん自動継続を止めて原因を再検討する。

```text
完了条件未達
  ↓
自動継続停止
  ↓
ChatGPTが原因分析
  ↓
指示不足 / プロンプト不備 / 実装ミス / 環境要因 / 仕様判断必要 等に分類
  ↓
修正方針
  ↓
再実行またはBLOCKED
```

## 9.2 Retry

Retryは、同じ正しい処理が一時的要因で失敗した場合の再試行に限定する。

設計、指示、プロンプト、実装方針が正しいか分からない状態ではRetryしない。

Retry上限は全処理共通の固定値にせず、処理種類ごとに後続仕様で定義する。

## 9.3 Replan

原因が設計・指示・工程にある場合はRetryではなく再計画・再指示として扱う。

無制限に再計画を繰り返さない。上限または人間判断へ戻す条件を後続仕様で定義する。

## 9.4 同一失敗

同一失敗を検知するため、単なるエラー文ではなく、工程、実行対象、エラー種別、原因分類、失敗箇所等を使ったFailure Signatureを持てるようにする。

具体形式は後続仕様で確定する。

## 9.5 BLOCKED

BLOCKEDはAIだけで自動継続できない状態である。

```text
BLOCKED
  ↓
人間判断
  ↓
再開 / 中止
```

仕様判断が必要、方針が一意でない、許可範囲外、原因特定不能、同一失敗の反復、必要承認未取得等の場合にBLOCKEDへ移す。

---

# 10. 完了判定

次を混同しない。

```text
作業実行済み
静的確認済み
テスト済み
外部反映済み
実画面確認済み
人間確認済み
完了確定
```

責任分担は次とする。

- Aegis Mesh：定義済み完了条件の成立確認
- ChatGPT：結果の意味を解釈し、次の判断を行う
- 人間：人間確認が完了条件に含まれる場合のみ確認
- 実装者AI：Result PacketとEvidenceを返す

実装者AI自身の完了宣言だけで完了確定しない。

---

# 11. CHAT_CURRENT / TASK_CURRENT

`tasks/CHAT_CURRENT.md` は設計・管理側の判断、指示、差戻し、工程判定の履歴である。

`tasks/TASK_CURRENT.md` は実装側の変更、テスト、残件、結果の履歴である。

両方とも仕様正本ではない。

## 11.1 CHAT_CURRENT更新ゲート

ChatGPTによる以下を管理イベントとして扱う。

- 判断
- 指示
- 差戻し
- 工程判定

管理イベント発生時は、対応するCHAT_CURRENT更新を必須とする。

最低限、日時、event_id、種別、対象工程、参照正本とSHA、判断理由、実施内容、結果、次の状態、未決事項を記録する。

Aegis Meshは更新後のGitHub上の実体を再確認し、内容とSHA等で更新成功を検証する。

更新成功を確認できるまで、次を実行してはならない。

- 実装者AIへの指示送信
- 差戻し実行
- 管制状態遷移
- 次工程移行
- 完了確定

```text
管理イベント
  ↓
CHAT_CURRENT更新
  ↓
GitHubで更新確認
  ↓
後続操作を解放
```

CHAT_CURRENTが未更新、更新失敗、確認不能の場合は自動継続を止める。

## 11.2 TASK_CURRENT

実装側は工程実行後に対象工程、変更ファイル、テスト結果、外部作用、残件、次状態を記録する。

Aegis MeshはResult Packet、Evidence、TASK_CURRENT、GitHub実体の不整合を監視する。

---

# 12. Evidence

Aegis Meshは「AIがそう言った」ことだけを証跡とみなさない。

工程に応じて、正本SHA、commit、diff、PR、test結果、build結果、反映結果、生成物、画面確認結果、Result Packet、CHAT_CURRENT、TASK_CURRENT、人間承認記録等をEvidenceとして扱う。

必要証跡がない場合、その条件を必要とする工程は完了させない。

---

# 13. 許可スコープ

外部作用は、すべて毎回人間承認に戻すのではなく、工程またはタスク開始時に許可範囲を定義する。

最低限、次を持つ。

```text
scope
allowed_actions
forbidden_actions
side_effect_policy
approval_required_if
```

必要に応じてactor、repository、branch、path、environment、接続先、対象データ、期限、コスト上限等を追加する。

許可範囲内では個別再承認を不要とし、範囲外または条件不成立の場合だけ人間判断へ戻す。

重要な外部作用は、LLMが注意書きを守ることだけに依存させず、Aegis Mesh側の実行ゲートで許可条件を検証する。

現行の基本方針：

- Codex：デプロイ不可
- Claude Code：工程で許可され、必須テスト合格、変更範囲内、BLOCKEDなし、禁止事項抵触なしの場合のみ条件付きでデプロイ可能
- 新規外部接続、外部API追加、パッケージ追加、認証・権限変更、DBやスキーマ変更は人間判断
- 既存データを消す操作は専用の明示指示なしに実行しない

Git操作は対象repository、branch、工程、変更範囲が明示されている場合に、参照、作業branch、対象ファイル更新、commit、通常push、PR作成までを許可範囲内で自動化できる。mergeは条件付きとする。履歴破壊や指定外変更は許可しない。

---

# 14. ChatGPT / Codex親 / Subagents / Claude Code

## ChatGPT

設計・管理者AIとして、正本確認、要件整理、Work Contract作成、実行経路選択、Result Packet解釈、STOP後の原因分析、再指示、工程判定、CHAT_CURRENT更新を担当する。

## Codex親

現場監督として、作業分解、Subagent割当、並列実行、進捗統合、結果統合、実行結果と証跡の返却を担当する。

## Subagents

Codex親配下の実装実行系として、調査、実装、テスト、レビュー等を担当する。

## Claude Code

Codex親の恒常的な代替ではない。ChatGPTが工程要件、許可範囲、デプロイ要否等を見て工程単位で選択する別の実装実行経路とする。

どの実行系を使っても、Aegis Meshが状態、証跡、完了条件、許可範囲を同じ基準で管制する。

# 15. 人間とChatGPTが同じ状態を見る

人間だけが管制画面を見られる構成では不十分である。

ChatGPTも、人間向け画面の元となる同じ基礎管制データを直接読めることを基本要件とする。

ChatGPTはCodex親の報告だけに頼らず、現在工程、実行主体、テスト、Evidence、Retry、BLOCKED、未解決事項、人間確認待ち、正本不整合、CHAT_CURRENT / TASK_CURRENT更新状況を確認して判断する。

少なくとも次を確認する。

- 正本未確認では進めない
- Context Version不一致では進めない
- Work Contractなしでは実装開始しない
- 理解ゲートを通らなければ実行しない

- CHAT_CURRENT未更新で指示送信・状態遷移しない

- 完了条件未達時は一度止めて再検討する

- 人間がAI間のコピペ係にならない
- 実行履歴を後から確認できる

# 21. 正本体系

Aegis Meshは企画概要書1冊だけで実装へ進めない。

正本を見れば別の設計者でも同じ粒度の計画・工程・実装指示を作れるよう、少なくとも次の正本群を整備する。

```text
docs/正本/
├── 【Aegis Mesh】企画概要書.md
├── 【Aegis Mesh】要件定義書.md
├── 【Aegis Mesh】システム仕様書.md
├── 【Aegis Mesh】データ設計書.md
├── 【Aegis Mesh】API・内部関数仕様書.md
├── 【Aegis Mesh】画面仕様・画面遷移書.md
├── 【Aegis Mesh】外部連携・権限仕様書.md
└── 【Aegis Mesh】技術選定理由書.md
```

役割：

| 文書 | 固定するもの |
|---|---|
| 企画概要書 | 目的、思想、全体構造、役割、主要制約、成功条件 |
| 要件定義書 | 機能要件、非機能要件、制約、受入条件 |
| システム仕様書 | 状態、遷移、Work Contract、Result Packet、STOP / Retry / BLOCKED、ゲート、完了判定 |
| データ設計書 | Project、Task、Actor、Evidence、Unresolved、Approval、Retry、Event等の項目と関係 |
| API・内部関数仕様書 | API、内部関数、入力、出力、責務、エラー、呼出関係 |
| 画面仕様・画面遷移書 | 画面一覧、表示項目、操作、遷移条件 |
| 外部連携・権限仕様書 | GitHub、Vercel、ChatGPT、Codex、Claude Codeとの接続、認証、許可 |
| 技術選定理由書 | TypeScript、Vercel、GitHub等の採用理由、比較、制約 |

同じ定義を複数文書へ重複させて矛盾源を増やさない。

# 22. 正本から実装まで

後続文書は正本を短く要約するだけではならない。

```text
正本群
  ↓
計画書
  ↓
開発工程表
  ↓
工程別実装指示書
  ↓
実装
```

各段階で上位文書の制約を具体化する。

例としてCHAT_CURRENTゲートは、

```text
企画概要書
  更新成功前に後続禁止
      ↓
システム仕様書
  イベント、状態、検証方式、失敗時処理
      ↓
API・内部関数仕様書
  更新処理、検証処理、実行ゲート
      ↓
計画書
  設計・実装・検証するPhase
      ↓
開発工程表
  実装工程と完了条件
      ↓
実装指示書
  対象、処理、テスト、証跡
```

まで連鎖していなければならない。

計画書では各要件について、どの正本要件を実現するか、どのPhaseで設計・実装するか、どの成果物に反映するか、何をもって完了とするか、どのEvidenceで確認するか、次工程へ進む条件を明示する。

---

# 23. 後続正本で確定する詳細

現時点で詳細仕様として残る主な論点は次である。

- STOPを正式状態とするか制御動作とするか
- Failure Signatureの正式形式
- 処理種類ごとのRetry上限
- Replan上限・人間判断へ戻す条件
- ChatGPTが状態を読む具体方式
- Codex親が状態を更新する具体方式
- Subagent状態取得方式
- 自動接続の具体プロトコル
- 補助状態ストアの要否
- 最初の実証案件

これらを実装時に推測で補わない。

---

# 24. 成功条件

Aegis Meshの成功状態は次である。

- 正本を読んでいないAIが進めない
- 未確定事項を推測で埋められない
- 古いContext Versionで進めない
- Work Contract外の作業を進められない
- 指示・判断・差戻し・工程判定がCHAT_CURRENTへ残る
- 実装結果がTASK_CURRENTとEvidenceへ残る
- 完了条件未達を完了扱いできない
- 指示不備時に無意味なRetryを増やさない
- 同じ失敗の繰り返しを検知できる
- 人間とChatGPTが同じ状態を見る
- 人間はAI間の通信係ではなく必要な判断だけを行う
- ChatGPTや設計担当が変わっても正本群から同じ粒度の計画、工程、実装指示を再構成できる
- 実装担当が変わっても同じ制約と完了条件で実装できる
- AIが間違っても、その間違いが次工程の正しい前提として伝播しない

---

# 25. 結論

Aegis Meshの本質は、AIを賢くすることではない。

AIを無条件に信用せず、人間を監視係にせず、正本、契約、状態、証跡、許可範囲、完了条件を外部に固定し、条件を満たさない限り次へ進めないようにすることである。

Aegis Meshが保持すべき共通事実は、

```text
何をするのか
何をしてよいのか
何をしてはいけないのか
何を根拠にしているのか
今どこにいるのか
何を実行したのか
何を確認したのか
何が未確認なのか
なぜ止まっているのか
何をもって完了するのか
```

である。

人間、ChatGPT、Codex親、Subagents、Claude Codeがこの同じ事実を見て動き、Aegis Meshがその条件を管制する。それがAegis Meshの企画上の完成像である。
