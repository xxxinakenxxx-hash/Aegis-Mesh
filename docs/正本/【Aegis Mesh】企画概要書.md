# 【Aegis Mesh】企画概要書

## 0. この文書の位置づけ

この文書は、Aegis Meshについて、これまでの議論をゼロから整理し直した企画概要書である。

過去に作成したAegis Mesh企画書・概要書・草案は、この文書の作成元として使用していない。

この文書では、次の4点を誰が読んでも分かる状態にする。

1. Aegis Meshは何のための仕組みか
2. 人間・ChatGPT・Codex親・Subagents・Aegis Meshの役割は何か
3. 仕事がどのように流れ、どこで止まり、何をもって完了とするか
4. 最初に何を作り、どこまでを実証するか

---

# 1. 一言でいうと何か

**Aegis Meshは、複数のAIを安全に働かせるための「管制システム」である。**

AIに仕事をさせること自体が目的ではない。

重要なのは、

- AIが勝手に前提を足さない
- 正本を無視して進まない
- 未確定事項を推測で埋めない
- 工程を飛ばさない
- 同じ失敗を繰り返さない
- 完了していないのに完了扱いしない
- どのAIが今何をしているか分かる
- 人間とChatGPTが同じ状態を見られる

という状態を作ることである。

---

# 2. なぜ必要なのか

AIを複数使うと、処理能力は上がる。

一方で、管理しなければ次の問題が起きる。

```text
人間
 ↓
ChatGPT
 ↓
Codex親
 ↓
Subagent A
Subagent B
Subagent C
 ↓
結果が戻る
```

一見すると効率的だが、実際には途中で次が起きる。

```text
正本を読んでいない
        ↓
AIが前提を推測する
        ↓
その推測を次のAIが事実として受け取る
        ↓
別のAIがその前提で実装する
        ↓
テストは通る
        ↓
しかし、そもそもの前提が間違っている
```

Aegis Meshが防ぎたいのは、単発のミスそのものよりも、

**間違った状態が、正しい前提として次のAIへ伝播すること**

である。

# 4. 誰が何をするのか

| 役割 | 主な責務 | やらないこと |
|---|---|---|
| 人間 | 目的、方針、仕様判断、承認、差戻し、最終確認 | 未確定事項をAI任せで確定しない |
| ChatGPT | 設計・管理者AI。要件整理、優先順位、仕事の定義、結果の解釈、次の判断、工程ごとの実行経路選択 | 未確認事項を事実扱いしない、勝手に実装しない |
| Aegis Mesh | 状態、制約、証跡、完了条件、Retry、BLOCKED、承認待ちの管理 | 自分で勝手に仕様判断しない |
| Codex親 | 作業分解、Subagent割当、並列実行、進捗管理、統合、完了条件確認 | 仕様を勝手に変えない |
| Subagents | Codex親配下の実装実行系。調査、実装、テスト、レビュー等の実作業 | 指示範囲外へ勝手に広げない |
| Claude Code | Codex親とは別経路で、必要な工程に選択される実装実行系。許可範囲内の編集・テスト・条件付きデプロイ等を実行 | 独自に仕様を決めない。Codex親の恒常的な代替とはしない |

# 5. Aegis Meshの本当の役割

Aegis Meshは「もう1人のAI」ではない。

Aegis Meshは、AI同士の間にある**管制層**である。

## 5.1 管制する対象

```mermaid
flowchart LR
    R[正本]
    T[TASK / 工程]
    C[制約・禁止事項]
    S[現在状態]
    E[証跡]
    V[完了条件]
    X[Retry / BLOCKED]
    A[承認待ち]

    M[Aegis Mesh]

    R --> M
    T --> M
    C --> M
    S --> M
    E --> M
    V --> M
    X --> M
    A --> M

    M --> H[人間]
    M --> G[ChatGPT]
    M --> P[Codex親]
    M --> CC[Claude Code]
```

Aegis Meshが最低限管理するものは次のとおり。

- 正本は何か
- 今どの工程か
- 誰が担当しているか
- 何をしてよいか
- 何をしてはいけないか
- 何が完了条件か
- 何を変更したか
- 何を確認したか
- 何が未確認か
- 何回失敗したか
- BLOCKEDしているか
- 人間承認が必要か

# 7. 「止まる」ことを仕様にする

Aegis Meshでは、進むことだけでなく、**正しく止まること**を重要機能とする。

次の場合は停止する。

- 正本がない
- 正本を確認できない
- 計画書がない
- 開発工程表がない
- 対象工程の実装指示書がない
- TASK_CURRENT.mdがない
- 文書間で矛盾している
- 現在工程を進めるために必要な未確定事項が残っている
- 指定外変更が必要になる
- 許可範囲外の外部通信・権限変更・その他の外部作用が必要になる
- 同じ失敗を繰り返している
- 完了条件を満たしていない場合は次工程へ進まず、いったんSTOPして未達理由を再検討する

## 7.1 状態遷移の考え方

```mermaid
stateDiagram-v2
    [*] --> 未着手
    未着手 --> 実行中
    実行中 --> 確認中
    確認中 --> 完了
    確認中 --> 修正必要
    修正必要 --> 実行中

    実行中 --> BLOCKED
    確認中 --> BLOCKED
    BLOCKED --> 人間判断
    人間判断 --> 実行中
    人間判断 --> 中止

    完了 --> [*]
    中止 --> [*]
```


## 7.2 完了条件未達時の扱い

完了条件未達は、むやみに実装を継続する合図ではない。

```text
完了条件を満たしていない
  ↓
STOP
  ↓
ChatGPTが未達理由を分析・再検討
  ↓
プロンプト不備 / 指示不足 / 実装ミス / 環境要因 等に分類
  ↓
修正方針を定める
  ↓
再実行
```

人間判断へ戻すのは、仕様判断が必要、方針が一意に決まらない、許可範囲外の操作が必要、同一失敗を繰り返す、ChatGPT側で原因を特定できない、のいずれかに該当する場合とする。Codex親や実装実行系は、実行結果・失敗内容・証跡をChatGPTへ返す。

Retryは、同じ正しい処理が一時的なエラー等で失敗した場合の再試行とし、設計・指示・実装方針が正しいか不明なまま繰り返すことには使わない。

# 8. 正本と実装文書

Aegis Mesh案件では、文書の役割を混ぜない。

## 8.1 最小構成

```text
【Aegis Mesh】企画概要書.md
        ↓
【Aegis Mesh】計画書.md
        ↓
クロスレビュー
        ↓
【Aegis Mesh】未確定事項確認書.md
        ↓
必要な修正・確定
        ↓
【Aegis Mesh】開発工程表.md
        ↓
TASK_CURRENT.md
        ↓
工程ごとの実装指示書
        ↓
実装
```

| 文書 | 役割 |
|---|---|
| 企画概要書 | 何を作るか、なぜ作るか、基本構造 |
| 計画書 | どの順序で作るか |
| 開発工程表 | 工程番号、目的、完了条件、確認観点、変更対象 |
| 実装指示書 | その工程で実際に何をするか |
| TASK_CURRENT.md | 今どこまで進んでいるか |

Aegis Mesh自身も、他案件を管制する前に、この文書構造に従う。

# 9. 正本の扱い

正本は、AIの記憶やチャット履歴ではない。

正本は、案件の目的・仕様・判断基準を固定する外部文書である。

## 9.1 正本を起点にする理由

```text
チャット記憶だけ
  ↓
忘れる / 圧縮される / 解釈が変わる
  ↓
前提がずれる

正本あり
  ↓
毎回同じ基準に戻れる
  ↓
人間・ChatGPT・Codexが同じ前提を確認できる
```

正本がない場合は、ないことを明示する。

存在しない正本を、AIが勝手に想像して作ったことにしてはいけない。

# 10. ChatGPT・Codex親・実装実行系の関係

Aegis Meshの考え方では、ChatGPTとCodex親を同じ役割にしない。

## ChatGPT

**設計・管理者AIとして、何をするかと、どの実行経路を使うかを決める。**

- 目的を理解する
- 要件を整理する
- 優先順位をつける
- 仕事の塊を定義する
- 結果を読み解く
- 次に何をするか判断する

## Codex親

**どう実行するかを決める。**

- 作業を分解する
- Subagentへ割り振る
- 並列処理する
- 進捗を見る
- 結果を統合する
- 完了条件を確認する

## Subagents / Claude Code

**実装実行系として実作業を行う。**

- SubagentsはCodex親の配下で、調査・実装・テスト・レビュー等を行う
- Claude CodeはCodex親とは別の実行経路として、ChatGPTが工程要件・許可範囲・デプロイ要否を踏まえて工程単位で選択する

### Claude Code

- Codex親とは別の恒常的な管制主体ではない
- 工程の実装指示と許可範囲に従って編集・テスト等を行う
- デプロイは、対象工程で明示的に許可され、条件を満たす場合のみ実行できる

## Aegis Mesh

**ChatGPT・Codex親・実装実行系が正しい状態で動いているかを監視する。**

# 12. 管制画面

Aegis Meshでは、管制状態と実行主体の状態を分けて扱う。

- 管制状態：未着手 / 実行中 / 確認中 / 修正必要 / BLOCKED / 完了 / 中止
- 実行主体状態：待機 / 実行中 / 完了 / 失敗
- `人間確認待ち` は状態名ではなく、追加の確認フラグとして扱う
- `人間判断` はBLOCKED解除のための判断工程であり、管制状態とは分ける

人間向け管制画面は専用Web画面として実装し、Vercel上で提供する。

Aegis Meshの画面は、単なるTODO一覧ではない。

「AI組織が今どうなっているか」を見るための画面である。

## 12.1 最低限必要な表示

# 15. 自動操作の許可範囲

Aegis Meshでは、外部作用をすべて毎回人間承認に戻さない。

工程またはタスク開始時に、最低限次を定義する。

```text
scope
allowed_actions
forbidden_actions
side_effect_policy
approval_required_if
```

操作は次の3区分で扱う。

| 区分 | 扱い |
|---|---|
| 事前許可済み | 許可範囲内で自動実行 |
| 条件付き許可 | 定義済み条件を満たす場合のみ自動実行 |
| 範囲外 / 禁止 | 停止し、人間判断へ戻す |

許可範囲内では個別再承認を要求しない。許可範囲外、禁止操作、条件不成立の場合だけ停止する。

Aegis Mesh初期方針として、Codexはデプロイ不可、Claude Codeは対象工程で許可され、必須テスト合格・変更範囲内・BLOCKEDなし・禁止事項抵触なしの場合のみ条件付き自動デプロイ可とする。

## 15.1 Git操作

対象repository・branch・工程・変更範囲が明示されている場合、次を自動実行可とする。

- status / diff / log 等の参照
- 作業branch作成
- 対象ファイルの作成・更新
- commit
- 通常push
- PR作成

mergeは、対象工程で許可され、必須チェック合格、BLOCKEDなし、未解決事項が完了条件を妨げておらず、禁止事項に抵触しない場合のみ条件付き自動とする。

force push、履歴改変、repository削除、branch削除、指定外repository・branch・ファイル変更は禁止する。

## 15.2 その他の外部作用

| 操作 | 方針 |
|---|---|
| 既存の承認済み外部通信先への通信 | 条件付き自動 |
| 新規外部通信先 | 人間承認 |
| 外部API追加 | 人間承認 |
| パッケージ追加 | 人間承認 |
| 認証・権限変更 | 人間承認 |
| DB / スキーマ変更 | 人間承認 |
| 既存データ削除 | 原則禁止。専用の明示指示がある場合のみ実施可能 |

## 15.3 CHAT_CURRENT.md / TASK_CURRENT.md の責任分担

- `tasks/CHAT_CURRENT.md` の管理責任：ChatGPT（設計・管理者AI）
- `tasks/TASK_CURRENT.md` の工程後実績記入：Codex親 / 実装者AI
- Aegis Mesh：CHAT_CURRENT / TASK_CURRENT と実行状態・工程状態の不整合を監視
- 人間：仕様判断・承認・差戻し

### 15.3.1 CHAT_CURRENT更新ゲート

ChatGPT（設計・管理者AI）による次の行為は、Aegis Mesh上の管理イベントとして扱う。

- 判断
- 指示
- 差戻し
- 工程判定

管理イベントが発生した場合、`tasks/CHAT_CURRENT.md` の更新を必須処理とする。

`tasks/CHAT_CURRENT.md` には最低限、次を記録する。

- 日時
- 種別：判断 / 指示 / 差戻し / 工程判定
- 参照した正本と取得時点の版（取得できる場合はcommitまたはblob SHA）
- 判断理由
- 実施内容
- 結果
- 次の状態
- 未決事項

Aegis Meshは、管理イベントに対応するCHAT_CURRENT更新がGitHub上で成功したことを確認する。確認方法は、更新後のファイル内容とblob SHA等を用いて、更新前との差分が実在することを確認できる方式とする。

次の操作は、対応するCHAT_CURRENT更新がGitHub上で確認できるまで実行してはならない。

- 実装者AIへの指示送信
- 差戻し実行
- 管制状態の遷移
- 次工程への移行
- 完了確定

したがって、基本原則は次とする。

```text
管理イベント発生
  ↓
CHAT_CURRENT更新
  ↓
GitHub上で更新成功確認
  ↓
指示送信 / 状態遷移 / 次工程移行 / 完了確定
```

CHAT_CURRENTが未更新、更新失敗、または更新確認不能の場合は、その管理イベントに基づく自動継続を停止する。

# 20. Aegis Meshが防ぐ事故

## 事故1：正本を読んでいない

```text
正本未確認
  ↓
停止
  ↓
「正本未確認」と表示
```

## 事故2：未確定事項を勝手に補完

```text
仕様不明
  ↓
推測しない
  ↓
BLOCKED
  ↓
人間判断
```

## 事故3：実装済み＝完了と誤認

```text
実装済み
 ≠
テスト済み
 ≠
必要な確認済み
 ≠
完了

人間確認が完了条件に含まれる工程では、人間確認済みになるまで完了としない。人間確認を必要としない工程では、定義済みの完了条件を満たせばよい。
```

## 事故4：同じ失敗を繰り返す

```text
失敗
 ↓
Retry 1
 ↓
同じ失敗
 ↓
Retry上限
 ↓
BLOCKED
```

```mermaid
flowchart TB

    C <--> M
    H <--> M

    P --> S2
    P --> S3
    P --> S4
    S1 --> P
    S2 --> P
    S3 --> P
    S4 --> P
```

最終的に目指すのは、

**人間がすべてのAIを直接監視しなくても、ChatGPTが秘書・参謀として案件全体を把握し、Codex親が現場監督として実行を管理し、Aegis Meshがその間の正本・状態・制約・証跡・完了条件を共通事実として保持する状態**

である。

# 22. 結論

Aegis Meshの本質は、AIをたくさん動かすことではない。

**AIが、正しい前提・正しい範囲・正しい工程・正しい完了条件で仕事をしているかを、人間とChatGPTが同じ事実を見ながら管制できるようにすること**である。

Aegis Meshが成功した状態は、

```text
AIが増えた
```

ではない。

```text
AIが増えても、人間が混乱しない
AIが間違っても、間違いが次工程へ伝播しない
AIが止まるべきところで止まる
人間が必要な判断だけを受け取れる
```

状態である。
