# 2. 技術選定の判断軸

Aegis Meshの技術選定は、一般的なWebアプリ開発の利便性だけではなく、以下の企画・要件を満たすことを最優先とする。

## 2.1 正本・履歴を外部に固定できること

Aegis Meshは、AIの記憶やチャット履歴だけに依存しない。

技術基盤は少なくとも以下を実現できなければならない。

- 正本文書を外部管理できる
- 文書の版を特定できる
- commitまたはblob SHAでContext Versionを確認できる
- 変更履歴を後から追える
- CHAT_CURRENT / TASK_CURRENT / Evidenceを保持できる

対応要件：
- REQ-CANON-01
- REQ-CANON-02
- REQ-CHAT-04
- REQ-EV-01
- REQ-GH-01
- REQ-NF-03

## 2.2 人間とChatGPTが同じ状態を参照できること

人間だけが画面を見られる構成、またはChatGPTだけが別の状態を読む構成は不可とする。

技術基盤は、同じ基礎管制データを人間向けUIとChatGPTの双方から参照できる構造にできなければならない。

対応要件：
- REQ-SHARED-01
- REQ-SHARED-02
- REQ-SHARED-03
- REQ-UI-01

## 2.3 AIの自己申告ではなく証跡で確認できること

「完了しました」というLLMの文章だけで状態を確定しない。

技術基盤は、commit、diff、PR、test結果、build結果、Result Packet、CHAT_CURRENT、TASK_CURRENT等をEvidenceとして保持・照合できる必要がある。

対応要件：
- REQ-RP-02
- REQ-DONE-03
- REQ-EV-01
- REQ-EV-02
- REQ-TASK-02

## 2.4 非LLMゲートを実装できること

デプロイ、削除、権限変更等の重要操作は、LLMのプロンプト遵守だけに依存させない。

技術基盤は、許可スコープ・条件・状態を機械的に確認し、条件不成立なら実行させない構造を実装できる必要がある。

対応要件：
- REQ-AUTH-01
- REQ-AUTH-03
- REQ-AUTH-04
- REQ-AUTH-05
- REQ-AUTH-06

## 2.5 AI間連携を自動化できること

最終的には、

```text

  ↓

  ↓
実装実行系
  ↓
Aegis Mesh
  ↓
ChatGPT
```

の閉ループを、人間の恒常的なコピー&ペーストなしで成立させる必要がある。

対応要件：

# 3. GitHub採用理由

## 3.1 正本上の位置づけ

GitHubはAegis Meshそのものではない。

GitHubは、以下を保持する基盤として採用する。

- 正本
- 開発工程表
- 実装指示書
- CHAT_CURRENT
- TASK_CURRENT
- Evidence
- commit
- branch
- PR
- test結果
- 変更履歴
- 状態管理のベース

## 3.2 採用理由

### 理由1：正本の版を固定できる

Aegis Meshでは、参照正本のpathに加え、commitまたはblob SHAを保持し、Context Versionを確認する必要がある。

GitHubを基盤にすることで、正本の内容と版を同じ場所で追跡できる。

対応要件：
- REQ-CANON-01
- REQ-CANON-02

### 理由2：変更履歴をEvidenceとして扱える

commit、diff、PR等をAegis MeshのEvidenceとして扱う要件がある。

GitHubはこれらを同一基盤上で保持できる。

対応要件：
- REQ-EV-01
- REQ-NF-03

### 理由3：CHAT_CURRENT / TASK_CURRENTと実装履歴を同一基盤で照合できる

Aegis Meshは、CHAT_CURRENT、TASK_CURRENT、Result Packet、Evidence、GitHub実体の不整合を監視する。

正本・履歴・実装変更を同じGitHub上で追跡する方針は、この照合要件と一致する。

対応要件：
- REQ-CHAT-04
- REQ-CHAT-05
- REQ-TASK-01
- REQ-TASK-02

### 理由4：Git操作そのものを許可スコープで制御対象にできる

対象repository、branch、工程、変更範囲を明示してGit操作を許可し、指定外変更や履歴破壊操作を禁止する要件がある。

GitHubはAegis Meshの許可スコープと直接結び付く主要な外部作用基盤となる。

対応要件：
- REQ-AUTH-01
- REQ-GH-02
- REQ-GH-03
- REQ-GH-04

## 3.3 GitHubだけでは満たせないもの

GitHubを採用しても、それだけでは以下は実現しない。

- 状態遷移ゲート
- Work Contract
- 理解ゲート
- Retry / Replan / BLOCKED制御
- 完了条件判定
- 非LLM外部作用ゲート
- ChatGPT / Codex / Claude Code間の自動接続
- 人間向け管制UI

したがって、

```text
GitHub
= 正本・履歴・Evidence・状態管理のベース

Aegis Mesh
= その情報を使って実行条件と状態遷移を管制するシステム
```

と分離する。

# 4. Driveを正本・実行時参照元にしない理由

企画概要書・要件定義書では、Aegis Mesh固有の正本をGitHub `docs/正本/` に固定し、Drive上の旧資料・ミラーを正本・実行時参照元として扱わないことが確定している。

## 採用方針

```text
GitHub docs/正本/
= Aegis Meshの正本

Drive
= Aegis Meshの正本・実行時参照元にはしない
```

## 理由

Aegis Meshでは、Context Versionをcommitまたはblob SHAで識別し、タスク開始時と実行直前の正本一致を確認する。

正本参照をGitHubへ一元化することで、複数保存先による「どちらが正しいか」という曖昧さを管制対象から排除する。

対応要件：
- REQ-CANON-01
- REQ-CANON-02
- REQ-CANON-03
- REQ-NF-04

## 2026-10-19 承認判断の反映（8正本クロスレビュー）

この節はユーザー承認済みの方針を反映する。以前の記述と矛盾する場合、**現行の実行禁止を緩めず**、ここで明示した将来方針・保存先・判断ルールを優先して整合修正する。実装・自動接続の実証が完了したという意味ではない。

- ChatGPTは管理判断・実装指示・CHAT_CURRENTの内容に責任を持つ。Aegis Meshは承認された管理イベントをGitHubへ反映し、再取得・SHAで検証する。実装側のTASK_CURRENTは、Codex経路ではCodex親がSubagents結果を統合して記録し、Claude Code経路では担当実装者が記録する。
- **仕事票（Work Contract）で依頼し、結果報告票（Result Packet）とEvidenceで結果を返す**既定の方式を維持する。契約提示→担当AIの理解確認→許可条件検証→実行開始の順とし、契約を受け取る前に理解確認を要求しない。Codex親は分担先Subagentsにも各自の担当範囲・禁止事項・完了条件を確認させる。
- 1工程につきChatGPT作成の実装指示書1本を基本とする。Codex親は工程の契約内で安全に作業を分割してSubagentsへ並行割当できる。担当範囲・依存関係・同一ファイルやbranchの更新競合を管理し、安全でなければ順次実行にする。別工程の並行実行には工程別の指示書を用いる。初期実証は1案件、画面は複数案件対応可能な設計を維持する。
- 正本・仕事票・結果報告票・管理状態・承認・Retry/BLOCKED/再計画記録・Evidence等の**永続的な保存先はすべてGitHubリポジトリ**とする。補助DB等を前提にしない。頻繁な更新、競合、性能の実証はGitHubで行い、方針変更は人間判断とする。秘密情報そのものはGitHubに保存しない。
- ChatGPTが選択する実行系はCodex親またはClaude Code。通常選択には都度人間承認不要。新規権限・許可外操作が必要な場合のみ必要な人間判断へ戻す。
- 進捗の機械的な受付や結果受領はAegisが検証できる。一方、**ChatGPTの判断・指示・差戻し・次工程移行・完了確定**はCHAT_CURRENTへの記録・GitHub再取得確認を経る。自動状態更新により管理イベントゲートを迂回してはならない。
- mergeは、対象工程での許可、必須チェック・テスト・レビュー、BLOCKEDでないこと、完了を妨げる未解決事項がないこと、禁止事項に抵触しないこと、必要な承認・承認条件成立を確認した場合のみ許可する。
- **条件付き承認は条件の文書化を必須**とする。対象操作、許可範囲、条件、確認方法とEvidence、判断者を記録し、条件成立を機械的に照合できなければ実行しない。確認済み（結果を見た）と承認済み（操作を許可した）は別記録。
- 失敗時はまず自動継続を停止し、一時的障害で同じ正しい処理と確認でき、二重実行の危険がない場合のみ上限付きRetry。指示・設計・コードの問題はChatGPTが分析し再計画（Replan）。解決不能・権限外・判断必要時はBLOCKEDとし、人間が再開か中止を判断。**判断理由・修正指示・BLOCKED解除などの管理履歴はCHAT_CURRENTに残し**、実行の技術的事実はTASK_CURRENT/Evidenceへ残す。Retry／Replan上限の具体値は実証・工程別仕様で決定する。
- Aegisの画面は人間がAIを巡回するためでなく、進捗・停止理由・判断対象を確認するためのもの。取得できない最新状態を成功・正常と偽らず、人間判断の対象・効果を明示し、同一判断の二重受付を防ぐ。
- AI間の仕事票の受け渡し・結果回収という設計を再審議しない。**物理的な自動送受信経路・起動・認証・復旧**について実証が残る。人間のコピー＆ペーストを恒久的な接続方式にしない。

### Codexデプロイの現在ルールと将来解禁（重要）
**現時点ではCodexからのデプロイ禁止を維持する。** ただし恒久禁止ではなく、ChatGPTの指示品質とAegisのチェック体制を確立・実証した後に、Codexも条件付きでデプロイできる状態を正式な将来目標とする。解禁は正本改訂と承認・実証を経て発効させ、現時点のデプロイ権限を拡張しない。

解禁に最低限必要な5条件：
1. ChatGPTの実装指示書に**デプロイ先、対象範囲、必要なテスト、禁止事項、完了条件**が明記されている。
2. Aegis Meshが**指示内容と許可範囲の整合を実行前**に確認する。
3. Codexの**必須テスト完了とEvidence**が確認できる。
4. **デプロイ直前**に対象環境・変更内容・BLOCKEDの有無・許可条件を再確認する。
5. **デプロイ後**に結果を検証し、失敗時には停止してChatGPTが原因を分析する。

これらのうち条件付き承認に該当する場合、**その条件を文書化・記録し、条件成立を確認してから実行する**。現状のClaude Code条件付きデプロイにも同じ原則を適用する。
