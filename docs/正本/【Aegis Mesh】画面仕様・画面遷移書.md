# 【Aegis Mesh】画面仕様・画面遷移書

更新日：2026-10-19  
状態：正本案（クロスレビュー・承認前）

## 0. 文書の位置づけと設計原則

本書は、Aegis Meshの**人間向けVercel管制Web画面**に必要な画面、表示情報、利用者の操作、画面間遷移、操作の許可条件・拒否時挙動を定義する。

根拠：企画概要書§1〜20、要件定義書REQ-STATE/REQ-CTRL/REQ-DONE/REQ-CHAT/REQ-AUTH/REQ-SHARED/REQ-UI/REQ-CONN、システム仕様書§8〜23、データ設計書D-01〜D-20、API・内部関数仕様書API-01〜15、外部連携・権限仕様書§1〜10、技術選定理由書§7。GitHubの正本・履歴とAegisの機械的な実行条件を画面から変更しない。

Aegis MeshはAIの作業を人間が常時監視するツールではない。**人間が必要な判断だけを行い、ChatGPTは同じ基礎管制データから仕事を判断する**。画面が表示・操作可能であることと、AI間の自動接続が動作することは別の受入条件である。

画面構成（S-01〜S-07）と遷移（T-01〜T-17）は、本書で提案する具体設計。URL、ルーティング方式、ピクセル配置、デザイン・認証実装は未確定。下位の詳細UIを勝手に採用済みと扱わない。

## 1. 共通表示の必須条件

全画面で可能な限り、対象案件・工程・タスクの識別、最後に検証できた状態と取得時点、参照正本・Context Versionの整合状況、更新失敗・取得不能を区別して表示する。状態を取得できない場合、以前の正常状態を最新として誤認させない。画面の「完了」という表示は、実装者AIの自己申告ではなくAegisの判定と必要なEvidenceに紐づける。

- **管制状態**：未着手、実行中、確認中、修正必要、BLOCKED、完了、中止。
- **実行主体状態**：待機、実行中、完了、失敗。管制状態とは別表示。
- **人間確認待ち**：管制状態に追加せず、独立したフラグとして表示。
- **操作許可**：scope、allowed_actions、forbidden_actions、approval_required_if、actor・repository・branch・path等の対象条件を根拠にする。
- **証跡**：GitHubのcommit／SHA／PR／テスト結果／Result Packet／CHAT_CURRENT／TASK_CURRENT等への参照と、その照合成否を表示する。
- **共通状態**：画面表示はSharedControlView（データ設計書D-20、API-09/FN-21）を使用し、ChatGPTが読む基礎データと分離した独自の「画面だけの正しい状態」を作らない。

## 2. 画面一覧と責務

| 画面ID | 画面名 | 目的・閲覧対象 | 必須の情報／主要操作 |
|---|---|---|---|
| S-01 | 案件管制一覧 | 複数案件の現在地と人間が判断すべき事項を把握 | 案件、現在工程、管制状態、担当実行系、最終更新、BLOCKED、未解決事項、人間確認待ち、CHAT/TASK整合、詳細へ移動 |
| S-02 | 案件・工程詳細 | 対象案件の工程・タスクの状態、契約、証拠、依存を把握 | project_id/process_id/task_id、目的・完了条件、管制状態、正本・Context Version、Work Contract、テスト結果、証跡、次工程へ進める条件、関連画面へ |
| S-03 | 実行主体・タスク状況 | Codex親／Subagents／Claude Codeの実行関係を把握 | 親・配下の識別、担当タスク、実行主体状態、現在作業、Result Packet要点、実行系別の失敗・未報告、タスク詳細へ |
| S-04 | 結果・証跡・履歴照合 | 「完了した」の裏付けを確認 | Result Packet、claims、diff、changed_files、tests/test_results、Evidence、GitHub実体、CHAT_CURRENT/TASK_CURRENTの記録・照合結果、未解決事項 |
| S-05 | 停止・BLOCKED・再検討 | 理由が不明な再試行や誤った次工程移行を防ぐ | 未達条件、STOPした事実、原因分析の現在地、Retry／Replan履歴、Failure Signature参照、BLOCKED理由、人間判断が必要な場合の判断画面へ |
| S-06 | 人間判断・承認 | 権限外操作やBLOCKED後の再開／中止等、人間の判断だけを受け付ける | 判断の対象・理由・影響範囲・許可スコープ・Evidence・選択肢（許可／却下／再開／中止のうち該当するもの）・判断結果 |
| S-07 | 正本・接続・管制整合 | 正本版や管理イベントの欠落が実行に伝播していないかを確認 | canonical_refs/SHA、Context Version、CHAT_CURRENT更新確認、TASK_CURRENT整合、管理イベント、接続・状態取得結果、最終検証時点、取得不可・競合・未確定 |

S-01〜S-07は情報設計上の画面単位であり、独立URL・タブ・ダイアログのどれで実装するかは未確定。工程表・実装指示書では画面単位を追跡可能にする。

## 3. 各画面の表示・操作・制約

### S-01 案件管制一覧

表示：案件ごとに現行工程、管制状態、実行主体、重要な異常、最終更新。**人間が今判断する必要がある案件を見落とさない**ことを優先する。通常進行中の各AIを人間が個別に巡回しなくてもよい。

操作：案件選択でS-02へ、BLOCKEDの詳細でS-05へ、判断待ちでS-06へ。一覧操作で管制状態を直接「完了」「実行中」に上書きしない。

### S-02 案件・工程詳細

表示：工程の目的と完了条件、参照正本path・SHA、Context Version検査、Work Contract（許可・禁止・成果物・条件）、タスクと管制状態、Result Packet／Evidenceの照合、次工程条件、未決事項。

操作：タスク状況S-03、Evidence S-04、例外S-05、版・履歴S-07へ。次工程移行はChatGPTの管理判断・CHAT_CURRENT更新ゲート・その他の条件を満たして初めて成立し、画面上の単純クリックだけでは確定しない。

### S-03 実行主体・タスク状況

表示：Codex親を現場監督として、その配下の各Subagentを区別する。Claude Codeは別の実行経路として明示する。タスク割当、現在作業、待機／実行中／完了／失敗、親の統合状況、報告の最新性、証跡への導線。

操作：対象タスクのS-02、Result PacketのS-04、失敗のS-05へ。Subagentの自己申告だけで工程を完了にしない。実行経路の選択責任はChatGPTであり、画面利用者が許可外に実行系を切り替える操作を設けない。

### S-04 結果・証跡・履歴照合

表示：主張（claims）と実際の変更ファイル／差分／テスト実行・合否／外部反映／人間確認を対比。以下は**別々の判定**として示す：作業実行済み、静的確認済み、テスト済み、外部反映済み、実画面確認済み、人間確認済み、完了確定。CHAT_CURRENTのevent_id・GitHub反映確認、TASK_CURRENTと結果・Evidenceとの不整合も表示。

操作：対応するS-02、停止理由S-05、正本・管理履歴S-07へ。証跡不一致や確認不能時に「完了」と表示しない。

### S-05 停止・BLOCKED・再検討

表示：完了条件未達／自動継続停止／原因分析中／再指示の必要性と、BLOCKEDを区別する。Retryは一時的失敗の同一処理に限定し、ReplanはChatGPTによる指示・工程の再検討として区別。原因未特定の同一修正反復を成功手順として提示しない。

操作：原因・証跡のS-04、詳細S-02へ。BLOCKED時に人間判断が必要ならS-06へ。**STOPを別の管制状態として表示するか**、BLOCKED解除後の正式遷移先は未確定（U-01、システム仕様書§9.6）であり独自の状態遷移を追加しない。

### S-06 人間判断・承認

表示：何を許可／却下／再開／中止するか、要求主体、対象工程・repo/branch/path/環境、理由、既存許可との違い、リスク・副作用、必要なEvidence、判断後に許可される範囲。該当しない選択肢は利用させない。

操作：許可、却下、BLOCKED再開、中止など該当する人間判断をAPI-13へ送る。判断の後もCHAT_CURRENT更新・版一致・契約・外部作用ゲートを迂回せず、Aegis側の検証成功で初めて後続が解放される。Codexのデプロイは表示上も実行不可。Claude Codeのデプロイは、許可され必要テスト等の条件を満たす工程だけに限る。事前許可内の通常操作を毎回人間に承認させない。

### S-07 正本・接続・管制整合

表示：正本のrepository/path/SHA、Context Version照合、管理イベントevent_id、CHAT_CURRENT更新前後SHA・再取得結果、TASK_CURRENT整合、Result Packet・Evidenceとの照合、取得不能・競合・接続障害の事実を表示する。未確認の接続先を「接続成功」と表示しない。

操作：案件詳細・証跡・停止理由へ戻る。技術的に不明な接続方式や機密トークンを画面で露出させない。GitHub以外の旧Drive文書を正本候補として選択させない。

## 4. 画面遷移表

| ID | 遷移元 → 遷移先 | きっかけ | 遷移時条件と禁止事項 |
|---|---|---|---|
| T-01 | S-01 → S-02 | 案件選択 | 権限内の案件のみ表示 |
| T-02 | S-01 → S-05 | BLOCKED／停止詳細 | 対象タスクの事実・理由を表示 |
| T-03 | S-01 → S-06 | 人間判断待ち | 人間確認待ちフラグ・権限に一致する対象のみ |
| T-04 | S-02 → S-03 | 担当AI／タスク状況を開く | 対象のActorAssignmentのみ |
| T-05 | S-02 → S-04 | 結果・証跡を開く | 同一task_id／process_idに対応させる |
| T-06 | S-02 → S-05 | STOP／Retry／BLOCKEDを確認 | 未完了を自動完了扱いしない |
| T-07 | S-02 → S-07 | 正本・履歴を確認 | 正本版と更新確認の結果を表示 |
| T-08 | S-03 → S-04 | Result Packet選択 | 実行主体とタスクが一致する結果のみ |
| T-09 | S-03 → S-05 | 失敗・未応答の詳細 | actor状態の「失敗」と管制BLOCKEDを混同しない |
| T-10 | S-04 → S-02 | 工程へ戻る | 閲覧遷移は状態遷移を発生させない |
| T-11 | S-04 → S-07 | 更新・証跡元を確認 | GitHubへの実在参照、SHA等を示す |
| T-12 | S-05 → S-04 | 停止・失敗の証拠を見る | エラー文だけで同一失敗と断定しない |
| T-13 | S-05 → S-06 | BLOCKEDの人間判断 | **人間の判断だけが再開／中止を決める** |
| T-14 | S-06 → S-05 | 判断保留・不成立 | 画面を移るだけでBLOCKEDを解除しない |
| T-15 | S-06 → S-02 | 判断受付後の結果確認 | API-13の記録、管理イベントの反映確認、許可条件が成立した結果のみを表示 |
| T-16 | S-07 → S-02 | 対象工程へ戻る | 不整合の事実は解除されるまで維持 |
| T-17 | S-02〜S-07 → S-01 | 案件一覧へ戻る | 戻る操作自体では状態・承認を変更しない |

画面遷移と**管制状態の遷移は別物**。たとえばS-05→S-06→S-02は画面表示の移動であって、BLOCKED→実行中が成立したことを意味しない。

## 5. 画面操作と論理APIの対応

| UIで行うこと | 使用する論理境界 | UI側での保証事項 |
|---|---|---|
| 案件・状態を表示 | API-09／FN-21 | 人間とChatGPTで同じ基礎管制状態を参照 |
| 正本版・管理履歴を確認 | API-01、API-02、API-15 | 読取失敗・不一致を明示 |
| Work Contractと理解結果を確認 | API-04、API-05の検証結果 | 未成立で「開始可能」としない |
| 実行報告・Evidenceを照合 | API-07、API-08、API-11 | 主張と証跡を分け、未確認を完了にしない |
| 停止・失敗・再検討を見る | API-14、API-10の判定 | RetryとReplanを誤誘導しない |
| 人間判断を提出 | API-13、API-12 | 人間認証・対象・操作権限の検証を経る |
| 判断後の次工程を確認 | API-03、API-10、FN-07／FN-08 | CHAT_CURRENTのGitHub再確認前に後続操作を解放しない |

上記APIは既存正本上の**論理名**。ブラウザのHTTPリクエストやエンドポイントが確定したわけではない（U-15）。

## 6. 権限・異常表示・安全条件

- **閲覧**：案件／タスクのアクセス権に従い、他案件のコンテキスト・秘密情報を混入させない。具体認証方式はU-11。
- **人間判断**：S-06で対象・影響・根拠を提示し、許可範囲外を自動承認しない。承認者・判断証跡を残す。
- **実行操作**：画面側でボタンを隠す／無効化するだけでは権限ゲートにならない。Aegisの非LLMゲートが実際の許可を判定する。
- **状態取得障害**：失敗、更新遅延、未検証、未確定を区別する。見えない実行は成功扱いしない。
- **管理履歴障害**：CHAT_CURRENTへの追記・再取得確認が失敗したとき、操作成功の表示と管理後続操作を禁止する。
- **Evidence不足／TASK_CURRENT不整合**：完了確定を抑止し、該当原因への導線を示す。
- **BLOCKED**：解除は人間判断。再開条件や未確定な具体遷移先を独自に決めない。
- **Codexデプロイ禁止**：画面からも抜け道を用意しない。
- **許可範囲内の自動処理**：人間に不要な確認やコピペを要求しない。

## 7. 最小受入シナリオ（画面単体と実連携を区別）

1. S-01で1案件の工程、管制状態、実行者、異常、人間判断待ちが見える。
2. S-02から親・Subagents／Claude Codeの区分、Work Contract、Context Version、Evidenceを追跡できる。
3. S-04で「テスト未実施」と「テスト合格」を区別し、不足するEvidenceが完了扱いされない。
4. 管理イベントのCHAT_CURRENT反映失敗がS-07へ表示され、次の指示や状態遷移が解除されない。
5. S-05で失敗理由が追跡でき、無意味なRetryが提示されず、BLOCKEDならS-06へ人間判断を求める。
6. S-06で権限・条件を明示し、範囲外操作／Codexデプロイを実行できない。
7. 人間とChatGPTが同じ元データを参照でき、結果を食い違う「最新状態」として扱わない。
8. 初期実証ではChatGPT→Aegis→実行系→Aegis→ChatGPTの自動往復が実際に成立し、人間がコピーしない。
9. 案件切替によって別案件の契約・証跡が混入しない。

受入シナリオを記したことは、実装・実証の完了を意味しない。
