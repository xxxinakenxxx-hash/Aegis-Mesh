# 【Aegis Mesh】外部連携・権限仕様書

更新日：2026-10-16
状態：正本案（クロスレビュー・承認前）

## 0. 位置づけ
ChatGPT（設計・管理）とAegis Mesh（TypeScript／Vercel）、Codex親・Subagents、Claude Code、GitHubを**ひとつの統制された自動ループ**として接続するための責務、信頼境界、許可スコープを規定する。根拠は企画概要書§2,3,5,11〜19、要件定義書 REQ-AUTH/REQ-GH/REQ-CONN/REQ-SHARED、システム仕様書§15〜23、技術選定理由書§3〜10。正本にない実現方式は確定しない。

「GitHubにファイルを置いた」「AI同士が読める」だけでは自動起動も結果返却も保証しない。初期実証からChatGPT→Aegis→実装系→Aegis→ChatGPTの**人間のコピペを必要としない閉ループ**を受入条件とする。

## 1. 基本接続と権限境界

| 主体 | 仕事と利用する経路 | 許可の原則 |
|---|---|---|
| 人間 | ChatGPTと相談／Vercel管制画面で判断・確認 | 目的、重要な仕様・許可範囲、条件外操作、BLOCKEDの再開／中止 |
| ChatGPT | Aegisへ管理判断・Work Contractを渡し、同じ管制基礎データを読む | 設計・管理・実行経路選択。直接の無条件実行権なし。CHAT_CURRENTゲートに従う |
| Aegis Mesh | 契約、Context Version、状態、Evidence、許可、管理イベントを検証し実装経路と接続 | 非LLMゲートを維持。実装そのものはしない |
| Codex親 | Aegisから許可済み仕事を受けてSubagentsへ分配・統合し結果返却 | 実装・テスト・許可済みGit操作。**デプロイ禁止** |
| Subagents | Codex親の管理下で実務を実施 | 親と契約の範囲内。個々のAIに独自の無制限権限を付与しない |
| Claude Code | ChatGPTが工程単位で選択した別の実装経路 | 実装等。条件が明示され満たされた時だけデプロイ可 |
| GitHub | 正本、計画、TASK、証跡、commit、PR、履歴、状態管理のベース | 対象repo/branch/pathを検査し、古いSHAで上書きしない |
| Vercel | Aegis本体と専用管制Web画面を動作させる | Codex/Claude CodeがVercel内で常駐できると仮定しない |
| Drive | Aegisの実行・正本参照経路に含めない | Drive旧版をGitHub正本の代替としない |

Claude CodeはCodex親の必須配下に固定しない。SubagentはCodex親の配下として管理し、Claude Codeは別実行経路として同じAegisのゲート・状態・証跡基準を適用する。

## 2. 情報の流れとゲート
1. ChatGPTがGitHubの承認済み正本と版に基づいてWork Contract・管理イベントを提出する。
2. AegisがWork ContractとContext Version、許可スコープを検査。**CHAT_CURRENTに記録し、GitHub再取得で記録の実在を検証**する。
3. Aegisは理解ゲート・操作別権限ゲートが成立した契約だけを、ChatGPTが選択した実行系へ渡す。
4. Codex親はSubagentsの作業を集約する。Claude Code経路の場合もResult Packet、状態、Evidenceを返す。
5. AegisはGitHub実体、TASK_CURRENT、結果、証跡を照合し、実行主体状態と管制状態を分けて保持する。
6. 人間の管制画面とChatGPTは**同一の基礎管制データ**を参照する。ChatGPTは結果を判断し、管理イベントを経て次の行動を決める。

具体の送受信実装（API、Webhook、Hooks、ポーリング、SDK、実行Workerなど）は未確定（U-05〜U-09）。いずれの方式を選ぶ場合も上記ゲートを迂回させない。接続可能性と初期実証での実動作は別に検証する。

## 3. 権限マトリクス

| 操作 | 人間 | ChatGPT | Aegis Mesh | Codex親／Subagents | Claude Code |
|---|---|---|---|---|---|
| 目的・重要仕様・事前許可設定 | 決定 | 提案・整理 | 記録・検査 | 独自変更不可 | 独自変更不可 |
| 正本・TASK参照 | 許可範囲で参照 | 参照し判断 | 取得と版検証 | 対象工程の範囲内 | 対象工程の範囲内 |
| 実装者選択 | 必要な承認 | 工程単位で選択 | 契約・権限検証 | 勝手な経路変更不可 | 勝手な経路変更不可 |
| 作業分解／Subagent実行 | 管制状態確認 | 工程の目的・制約指定 | 監視・ゲート | Codex親が担当 | 選択された工程内に限る |
| 設計・管理履歴（CHAT_CURRENT） | 確認 | 記録責任 | 記録・再取得検証・後続ゲート | 担当外の上書き不可 | 担当外の上書き不可 |
| 実装履歴（TASK_CURRENT） | 確認 | 照合 | 整合監視 | 実装者として更新 | 実装者として更新 |
| 許可範囲内Git更新／通常push／PR | 許可設定 | 範囲と結果を管理 | 範囲・版・競合を検査 | 指定工程で可 | 指定工程で可 |
| merge | 許可条件設定 | 条件・Evidenceを判定 | 条件ゲート | 無条件実行不可 | 無条件実行不可 |
| デプロイ | 許可スコープを設定 | 可否を判断・指示 | 条件ゲート | **禁止** | **条件付き可** |
| 新規外部接続／外部API追加／依存パッケージ追加／権限認証変更／DB・スキーマ変更 | 判断・承認 | 承認要求 | 未承認を拒否 | 独断不可 | 独断不可 |
| 既存データ削除／履歴破壊 | 専用明示指示の要否を判断 | 独断不可 | 拒否・必要承認検査 | 独断不可 | 独断不可 |
| BLOCKED解除 | 再開／中止を判断 | 根拠整理 | 決定の反映・ゲート | 自己判断再開不可 | 自己判断再開不可 |

権限は「AI製品の一般機能」ではなく、**工程ごとのWork Contractと許可スコープ**で決まる。事前許可済みなら範囲内で毎回承認を求めない。範囲外や条件不成立のみ人間に戻す。共通ルールより狭い工程権限を無視しない。

## 4. 操作別許可条件と禁止
- Git参照、作業branch、許可対象ファイル変更、commit、通常push、PR作成：repo、branch、工程、対象pathが指定され、Context Version整合、許可・禁止条件に抵触しない場合のみ実行可能。
- merge：定めたテスト・レビュー・完了条件が成立し、解決すべき未解決事項が残らず、必要承認を満たす場合のみ条件付きで許可する。具体のbranch保護設定は別途検証する。
- force push、履歴改変、指示外ファイル／repo変更：通常の自動操作として許可しない。別の操作としての明示承認が必要な場合も、現行正本の禁止事項を優先する。
- Codexのデプロイ：契約やユーザー指示の一般的な許可から推定せず、**禁止**。
- Claude Codeのデプロイ：対象工程に許可が明記され、必須テスト合格、変更範囲内、BLOCKEDなし、禁止事項抵触なし、CHAT_CURRENTゲート等が満たされたときに限る。デプロイ済み・反映済み・実画面確認済みを混同しない。
- 新規外部接続／API／パッケージ／認証・権限／DB変更：事前の人間判断が必要。既存データの削除は専用の明示指示なしには実行しない。
- タスクが途中で範囲外へ広がる場合：実行継続を止め、勝手に契約や権限を増やさない。
- 外部操作の成功はAPI応答だけではなく、必要な実体・証跡と照合する。

## 5. 信頼境界と認証・秘密情報
人間の承認、ChatGPTの指示、Aegis内部ゲート、実装者AI、GitHub／Vercelは別の信頼境界にある。自然言語の「許可されています」という報告だけで外部作用を許可しない。操作ごとに実行主体、対象、作用範囲、工程、許可・承認状態をAegisが検証する。

- GitHubの正本・更新競合：更新直前に最新版とblob SHA／コミットを照合し、SHA不一致時に古い内容を上書きしない。
- 管理イベント：GitHubのCHAT_CURRENT再取得が確認できるまで、指示送信・差戻し・状態遷移・完了確定は不許可。
- 対外APIや実行系への接続：実行主体の認証、要求元の真正性、最小権限、トークン保管・失効の要件を満たす必要がある。
- APIキー、トークン、Cookie、認証プロファイル等はGitHubへ保存せず、ログ・Evidence・Result Packetへ無用に出力しない。
- 認証方式、秘密情報保管先、権限の具体単位、期限とローテーションは**未確定（U-11）**。確認なしにOAuth、PAT、GitHub App、Vercel環境変数などを採用済みとはしない。
- ネットワーク到達、ローカル／クラウド実行の起動方法、Webhook防護は未実証である。GitHubのread/write成功とAI間の自動起動成功は同義ではない。

## 6. 管制状態の提供
管制画面とChatGPTは同じ基礎データを読み、現在工程・管制状態・実行主体・親／Subagents・Claude Code・テスト結果・Evidence・Retry・BLOCKED・未解決事項・人間確認待ち・CHAT/TASK更新状態・最終更新を照合できること。閲覧権限が異なる場合でも、同じレコードに対して整合する状態を示す。ChatGPT側の読取接続方式・認証・更新通知はU-05に属する。

## 7. 停止・失敗時の接続規則
- 正本取得不能、Context Version不一致、理解不足、契約欠落：実行系へ送信しない。
- GitHub CHAT_CURRENTの記録・再確認失敗：管理操作を解放しない。
- 外部作用の条件不成立：送信しない。必要なら人間判断。
- 実行系からのResult Packet不備・証跡不足：結果を完了確定しない。
- 完了条件未達：試行を増やさずSTOPしてChatGPTが原因を分析・再指示。
- Retry：一時的失敗に限定し、回数・条件未確定のまま無制限再試行を行わない。
- BLOCKED：人間の再開／中止判断なしに自動復帰しない。
- 接続断・同じ要求の再送：二重実行を防ぐ方式はU-09で決定する。未確定のまま成功保証を宣言しない。

## 8. 確認・実証条件
AC-01：ChatGPT→Aegis→Codex親／選択されたClaude Code→Aegis→ChatGPTの**自動ループ**を人間の転記なしで実測。
AC-02：ChatGPTと人間用管制画面が同じ実行状態・証跡を参照。
AC-03：正本・Context Version不一致なら実行不可。
AC-04：CHAT_CURRENT未記録なら指示送信不可。
AC-05：Codexからのデプロイ拒否、Claude Codeの条件未充足デプロイ拒否。
AC-06：許可範囲外変更・GitHub SHA競合・未承認外部作用を阻止。
AC-07：結果・証跡が欠ければ完了確定不可、BLOCKED解除は人間判断のみ。
AC-08：TASK_CURRENTと実体不整合を検出・保留。
AC-09：秘密情報をGitHubや外部提示結果に混入させない。
いずれも現時点で**実証済みとは記載しない**。

## 10. データ設計書との対応（2026-10-19追記）
- `Project／Process／Task／ContextVersion／CanonicalReference／WorkContract` は、外部実行系へ送る対象の同一性・正本版・工程範囲を拘束する。GitHubの対象repo・path・SHAを無視した指示送信は許可しない。
- `Actor／ActorAssignment／PermissionScope／Approval` を照合し、Codex親・Subagent・Claude Codeを混同せず、工程単位で実行権限を判定する。ActorAssignmentは無制限の権限付与ではない。
- `ManagementEvent／ChatCommitVerification` をすべての管理後続操作のゲートとし、CHAT_CURRENTのGitHub再取得確認なしに後続実行を解放しない。
- `ResultPacket／Evidence／TaskCurrentVerification／ControlStatus` を突き合わせ、実行報告のみで完了・デプロイ成功を確定しない。
- `SharedControlView` は人間とChatGPTが**同じ基礎管制データ**を見るための論理出力であり、公開APIや保存先の方式を意味しない。
- 論理レコードの物理保存方式・識別形式・保持条件は未確定（U-10／U-17）。接続・認証・公開APIの実方式はU-05〜U-11／U-15／U-16に従う。データ設計書の追加によって自動的に権限を拡張しない。
